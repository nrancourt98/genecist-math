# JS Project Architecture

Technical design for the JS port: `./project` (the shippable engine + backend) plus its surrounding tests/tooling at the repo root. See `docs/game-design-spec.md` for game rules and `docs/bgaming-compliance.md` for the protocol this serves. Plain JavaScript (CommonJS), Node.js, Express — no TypeScript, no game frontend (the `visualizer/` HTML page is a dev/debug tool, not the game's UI).

## Directory layout

**`project/` contains only what ships in the Docker image** - everything dev/test/tooling-only lives at the repo root, *outside* `project/`, on purpose (restructured for exactly this reason - see the judgment-call log's "repo restructure" entry). The Dockerfile only ever `COPY`s `project/engine/` and `project/backend/`; nothing under `tests/`, `sim/`, `devtools/`, or `visualizer/` can end up in the image even by accident, because it's not physically inside the directory the Dockerfile's COPY commands reach into.

```
(repo root)/
  project/                # the only directory the Docker image is built from
    engine/                 # pure game logic — zero HTTP/network dependencies
      config/               # paytable, paylines, reel loader, switch-spin weight tables, bet modes
      data/reelWeights.js   # tunable per-symbol weight tables - the actual design input
      data/generateReels.js # builds reels/*.csv from reelWeights.js, then converts to .json (`npm run gen-reels`)
      data/reels/           # BR0/FR0/FR1 as .csv (generated, not hand-authored) + .json (converted, committed)
      rng/                  # rngInterface (sync contract), localPrng (sim/tests), remoteRng (prefetch-buffered)
      board/                # drawBoard, switch-symbol overlay (drop + replace)
      wins/                 # lineEvaluator, wildMultiplier, wincap, units (centi-multiplier <-> cents)
      features/             # switchSpins state machine, freeSpins trigger/retrigger/upgrade, basePlus boost
      spin/                 # roundState shape + factories, spinStep.resolveOneSpin (the step-function), event builders
      index.js              # public engine API surface
    backend/                # Express app — own package.json + Dockerfile (BGaming container shape)
      src/app.js            # createApp() — route wiring, no listen() side effect (testable in-process)
      src/index.js          # process entrypoint: createApp().listen(), SIGINT handling
      src/playHandler.js     # the `play` method: round lifecycle, finance, bet-mode resolution
      src/rng/rngClient.js   # prefetch-buffered RngInterface backed by BGaming's RNG microservice
      src/godMode.js         # god_data → scripted RngInterface, gated by ENABLE_GOD_MODE
  tests/                  # unit (deterministic), statistical (weight-table/trigger-frequency), integration (HTTP contract)
  sim/                    # offline RTP/statistics CLI, reuses project/engine/spin/spinStep.js + localPrng
  devtools/               # mock-runner (manual HTTP smoke-testing) + the terminal event visualizer
  visualizer/             # standalone HTML event-log viewer (no build step, opened directly in a browser)
  package.json            # governs tests/sim/devtools/visualizer as one workspace - zero npm dependencies
```

**Workspace/Docker note**: `tests/`, `sim/`, `devtools/` (and `project/engine/`, by reference) share one root `package.json` - none of these four have any npm dependencies at all, so there's no `node_modules` to manage outside of `project/backend/`'s own. `project/backend/` has its own `package.json` + `Dockerfile` (BGaming's required container shape demands a self-contained backend image). The Dockerfile's build context is the **repo root**, not `project/backend/`, so it can `COPY project/engine/ ./engine/` alongside `COPY project/backend/ ./backend/` — otherwise `require("../../engine")` inside the container has nothing to resolve against. Called out explicitly so it isn't discovered as a deploy-time surprise.

## Data porting conventions

- **Paytable, paylines, switch-spin weight bags**: inline JS modules (not JSON), transcribed verbatim from the Python source, each entry/block commented with its exact `gamestate.py`/`game_config.py` line reference. Mechanical, no computation — kept easy to diff against the source by eye.
- **Reels**: NOT ported - the Python prototype's reel strips carry no meaningful RTP signal (see the judgment-call log's "Reel strips are designed fresh" entry). `engine/data/reelWeights.js` holds the actual tunable design input (per-symbol weight tables); `engine/data/generateReels.js` builds `engine/data/reels/*.csv` from those weights (`npm run gen-reels`), then converts to `*.json` (array-of-arrays of symbol names) via the same `convertOne()` that `engine/data/convertReels.js` exposes for hand-edited CSVs. The JSON output is committed; the engine never parses CSV at runtime.
- **Paytable storage**: pre-multiplied by 100 at module load (see Units below) so no runtime float multiplication ever happens.

## RNG abstraction

One synchronous interface (`engine/rng/rngInterface.js`): `randInt(max)`, `randRange(min,max)`, `pickFromBag(literalWeightedArray)`, `sampleWithoutReplacement(pool, n)`, `shuffle(arr)`. Two implementations:
- `localPrng.js` — fully synchronous, used by the simulation CLI and tests. Fast enough for millions of calls in a tight loop.
- `remoteRng.js` — backs onto BGaming's RNG microservice. Since that's a network call and the engine's interface must stay synchronous (so `resolveOneSpin` is identical whether driven live or in batch simulation), `remoteRng` **prefetches a batch (~32) of random values in one JSON-RPC call** before a spin is resolved, then serves the rest of that spin's draws synchronously from the buffer. The backend's `playHandler` does this prefetch *before* calling into the engine — the engine itself never awaits anything.

## Units

Every win amount inside the engine is an integer **centi-multiplier** (`multiplierOfBet × 100`) — confirmed against real book data (`payoutMultiplier:1160` ↔ `baseGameWins:11.6`). All internal math (line wins, multiplier sums, wincap comparisons, accumulators) stays integer. The only place floating-point-adjacent division happens is the single HTTP-boundary conversion `win_cents = round(centiMultiplier * bet_cents / 100)`, done once per `play` response — never inside the engine.

## The step-function

`resolveOneSpin(roundState, rng) -> { events, roundState, winDeltaCenti, isRoundFinal }` is the one function powering both the live backend (one call per HTTP `play` request) and the offline simulator (called in a tight synchronous loop). **One call resolves exactly one spin-equivalent of work** — one board reveal, its line evaluation, and whatever switch/free-spin bookkeeping that single board triggers. Never more than one `reveal` event per call. This is what makes a round naturally resumable across stateless HTTP calls.

`roundState` is plain JSON (numbers/strings/arrays/null only — no class instances, no Map/Set, no functions) so it survives an opaque `JSON.stringify`/`parse` round-trip through BGaming's Runner. Shape:
```
{
  betMode: "base"|"baseplus"|"bonus"|"super",
  betAmountCents: integer,
  phase: "base" | "freespins" | "done",
  basegameWinsCenti: integer,
  freegameWinsCenti: integer,
  cappedWin: boolean,
  switch: { spins: integer, symbols: string[], wild: boolean|null },
  freeSpin: null | { mode: "R"|"S", fs: integer, totFs: integer, reelSet: "FR0"|"FR1" },
  basePlusBoostApplied: boolean,
}
```

`backend/src/playHandler.js` drives it: on a round's first call (`round` is `{}`), seeds a fresh `roundState` via a per-bet-mode factory — `bonus`/`super` seed `phase:"freespins"` directly with the entry mode/reel pre-populated, so the very first `resolveOneSpin` call goes straight into free-spin resolution, never touching the base loop (this is how buy-a-feature works). The bet is charged (`finance.bet`) only on that first call; every subsequent step call reports `bet: 0` but still reports its own `win_change`. `round` resets to `{}` once `isRoundFinal`. `god_data` is only honored when `ENABLE_GOD_MODE=1`.

## Per-spin orchestration order

Verified against decompressed book events and the Python source's loop structure:
1. If a switch sequence is active, decrement `switch.spins`, emit `updateSwitchSpins` — **before** drawing this spin's board.
2. Draw the board.
3. Roll multipliers for natural W cells via `assignWildMultipliers` (free-spin modes only; a no-op assignment of 1 in base game) — must happen before step 5, since the `reveal` event's board needs each W's `multiplier` already set.
4. Maybe force-place a fresh SW (flat per-mode chance).
5. Emit `reveal`.
6. Apply switch-symbol replacement using the *current* cumulative `switch.symbols` (no-op if empty — covers the "triggering spin itself never gets replaced" case automatically, no special condition needed). Emit `switchingSymbols` only if something changed. Switch-created `W` cells don't have a multiplier yet at this point (they didn't exist during step 3).
6b. Call `assignWildMultipliers` a second time — idempotent, so naturally-drawn wilds from step 3 are skipped, and only the switch-created `W` cells from step 6 get a multiplier rolled. Must happen before step 7.
7. Evaluate lines; emit `winInfo`/`setWin`/`setTotalWin`.
8. If a fresh SW dropped this spin, roll and append the award; emit `newSwitch`/`newSwitchSpins`.
9. Wincap check (one shared function, called once here — not duplicated per phase, unlike the Python source which repeats this block four times near-verbatim).
10. Phase-specific trigger check: base phase checks classic-FS trigger; free-spin phase checks retrigger/upgrade.

## `baseplus` mode — rationale

No Python or BGaming-doc precedent exists for this mode at all (confirmed with the designer it's an intentional gap, not an oversight on our part). Proposal: cost 1.25× bet; once per round (guarded by `basePlusBoostApplied`, not per switch-extended sub-spin — keeps the RTP math from this knob simple and avoids effectively granting free re-rolls during a long switch sequence), a 1-in-14 independent chance to force-add one extra "S" onto the naturally-drawn board, on top of whatever landed naturally, evaluated right after `drawBoard` and before the FS-trigger check. Both the cost multiplier and the boost-chance weight are named constants, not magic numbers, specifically so the simulation CLI can re-tune them further — they are not load-bearing design decisions, just a concrete starting point (the boost chance was already lowered once from an initial 1-in-8 guess during the reel-strip balancing pass - see the judgment-call log). Originally this boost rolled a 50/50 between "S" and "S2"; that choice was removed when S2 was merged into S (see the judgment-call log entry below) since there's now only one symbol to place.

## Offline simulation / RTP CLI

`sim/simulate.js --mode <base|baseplus|bonus|super> --n <count> [--seed <n>]`, or `--all [--n <count>]` to sweep every mode in one invocation (default `n` per mode: base/baseplus 100k, bonus/super 50k, each round doing substantially more work). Imports the engine directly (no HTTP) via `resolveOneSpin` + `createLocalPrng`, looping per round until `isRoundFinal`. `sim/statsCollector.js` aggregates each round's outcome (derived only from `resolveOneSpin`'s public return shape - the events emitted and the roundState transitions visible to the loop, never reaching into engine internals beyond that contract); `sim/reportFormat.js` renders the summary. Reports per mode: RTP vs. the 96% target, hit rate, win volatility/std-dev, Switch-Spins trigger rate + average spins-per-sequence + wild/highest-symbol split (should converge ~50/50), classic-FS trigger rate split by R vs. S entry, wincap-hit rate. This is the project's primary math-documentation artifact for BGaming's submission requirements.

This CLI is also what surfaced that the original reel strips/switch-spin probabilities were nowhere near a 96% RTP target (see the judgment-call log entries on the line evaluator bug, the replacement-gating bug, switch-spins balancing, and reel-strip balancing) - all of that tuning was done by reading this CLI's output, adjusting a weight table or rate constant, and re-running, not by deriving target values analytically. Current first-pass numbers (100k-150k rounds/mode): base ~101%, baseplus ~92%, bonus ~96%, super ~88% - re-run at 1M+ per mode before treating any of this as final. A second, lower RTP variant (94-94.5%, per BGaming's suggestion) is explicitly out of scope for the first pass — the data/config layer should stay simple (hardcoded constants) rather than pre-building a multi-profile abstraction for a variant that doesn't exist yet.
