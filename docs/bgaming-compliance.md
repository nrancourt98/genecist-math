# BGaming Backend Compliance Notes

Extracted from `./info/docs/*` (Bgaming Publishing Technical Documentation.pdf, Game Publishing Process.pdf, How to provide game.docx, Pre_Submission_Checklist.docx, Publishing - Game Events usage.docx, Questions.txt) and the reference implementation at `./info/sample-game-main/`. Scoped to what's relevant for a **backend-only** deliverable — UI/localization/graphics/asset checklist items are out of scope and omitted here.

## Architecture

Our deliverable is a stateless **"game function"**: a Docker container exposing one JSON-RPC method, `play`, on an HTTP endpoint on port 80. It must have **no internal state, no side effects, no external dependencies** (no DB/cache/message broker) — every call is self-contained, fed all the state it needs and returning all the state that needs to persist.

```
Player <-> BGaming Runner (hosted) <-> our Game Function (this project) <-> BGaming Runner <-> Casino
```

BGaming's hosted **Runner** owns everything else: balance ledger, session, the `init`/`info`/`replay` RPC methods, multi-tab `state_lock` protection, freebets bookkeeping. None of that is implemented by us — the Runner calls our `play` method repeatedly, handing back whatever opaque JSON state we returned last time.

## The `play` contract

**Input** `params`:
```
{
  round: object,        // our own opaque state for the in-progress round; {} on a round's first call
  game: object,         // our own opaque state persisted across rounds in a session; {} if unused
  req: {
    bet: integer,                    // smallest currency unit (cents), always cast to integer
    bet_type: "bet" | "freebet",
    purchased_feature?: string,      // e.g. our own "buy_bonus" / "buy_super" values
    ...custom fields allowed
  },
  config: {
    rtp: string | null,              // selected RTP profile for the session
    purchased_features: string[],    // which buy-features are enabled for this operator/session
    gamble_limit: number | null,
  },
  god_data: object,      // dev-only override; MUST be ignored unless ENABLE_GOD_MODE=1
}
```

**Output**:
```
{
  round: object,         // updated opaque round state, passed back next call; {} once the round is final
  game: object,          // updated opaque session state (always {} for this game — no session-persistent mechanic)
  finance: [
    { type: "betting", bet: integer (negative), base: integer (positive), win_change: integer }
  ],
  resp: object,          // free-form, passed to the frontend — "only return absolutely necessary data"
  final: boolean,        // true once the round is fully resolved
}
```

## Multi-step bonus rounds (mandatory)

From the Pre-Submission Checklist: *"Financial info must be received at every step, not just the last step"* and *"Round can resume from any bonus step after connection loss."* This is why a bonus feature can't be computed in one giant `play` call — each `play` call must resolve **one spin-equivalent of work** (one board reveal + its evaluation + whatever feature bookkeeping that spin triggers), report that spin's own `finance.win_change`, and persist everything needed to resume in `round`. Reasons given in the docs:
- If the connection drops mid-feature, the player must be able to resume from the last completed step.
- Unfinished bonus rounds get force-closed after 24 hours; without per-step financial data, the platform can't correctly credit partial winnings (risk of deducting a stake without awarding accumulated wins — described as "unacceptable for most casinos, may lead to game removal").

## Max win cap (mandatory)

- Every game must declare a **Max Multiplier**. A single round's win must never exceed `base_bet × max_multiplier`.
- If an outcome would exceed it mid-round (e.g. inside a bonus feature), the round must terminate immediately, the win is **clipped to exactly the cap** (not zeroed — the player keeps everything earned up to the cap), and a max-win popup is shown.
- For this game: `max_multiplier = 10,000` (ported from `game_config.py`'s `wincap = 10000.0`).

## RNG

- Must use numbers generated by an external **RNG microservice**, never `Math.random()` or a seeded PRNG, for any live/production RTP-affecting decision. Per `Questions.txt`: *"Please use generated by RNG number but not seeds for the RTP calculations."*
- Reachable via `RNG_URL` env var (default `http://localhost:4002/api` in local dev). JSON-RPC methods:
  - `rand` — `{qty, type: "u32"|"f32"}` → `[numbers]`
  - `rand_range` — `{first, last}` → single integer in `[first, last]`
  - `sample` — `{enum: [ints], limit}` → array of selected items
  - `shuffle` — `{enum: [ints]}` → shuffled array
- Random numbers are 32-bit unsigned integers by default.
- Because a network round-trip per random draw is far too slow for the offline simulation tool (millions of draws), the engine's RNG is an injected interface: a synchronous local PRNG for simulation/tests, and a "prefetch a batch, serve synchronously from the buffer" wrapper around the remote service for the live backend.

## Currency handling

- At least 64-bit integers for all monetary values. **Never floats** (rounding risk) and never 32-bit (insufficient range for crypto currencies). Balance/bet/win values are in the smallest currency unit (cents).
- Internally, this engine works in integer "centi-multiplier" units (see `docs/game-design-spec.md`) and only converts to currency cents once, at the HTTP response boundary.

## Buy-bonus

- Triggered via `req.purchased_feature`. BGaming's own example games use an enum of `"buy_bonus" | "buy_chance" | "buy_bonus_and_chance"`, but the docs explicitly allow custom fields in `req` — we're free to define our own values (e.g. `"buy_bonus"` for the 100×/R-mode buy, `"buy_super"` for the 300×/S-mode buy).
- On a buy-feature round: `finance.bet = -(req.bet * bonus_multiplier)` where `bonus_multiplier` is the mode's cost multiplier (100 or 300). The frontend (not our concern) is expected to hide buy-bonus buttons when the relevant value isn't present in `config.purchased_features`.

## FreeBets

- Mandatory support, but it's mostly a Runner/frontend concern: when freebets are active, the client includes `bet_type: "freebet"` in `req`, and the bet value is computed from `config.freebets_limits[freebets.bet_level]` — the game backend's role is just to not error out when it sees `bet_type: "freebet"`. No special game-logic branching is required beyond accepting the field.

## GodMode (dev/test only)

- `god_data` lets a developer override RNG outcomes (e.g. `{"random": 2}`) to script deterministic test scenarios.
- **Must be ignored entirely unless `process.env.ENABLE_GOD_MODE === "1"`** — and must never affect production container behavior. The reference sample backend does NOT actually gate this (a known gap in that stub) — our implementation must add the gate explicitly.

## Docker

- One container, `FROM node:lts` (per the reference sample), listening on port 80 in production via `BACKEND_PORT` env var (default differs in local dev).
- Reference `Dockerfile`:
  ```
  FROM node:lts
  WORKDIR /app
  COPY package*.json ./
  RUN npm ci
  COPY . .
  ENV BACKEND_PORT=80
  EXPOSE 80
  CMD [ "node", "src/index.js" ]
  ```
- Our build context must be the **repo root** (not `project/backend/`) so the Dockerfile can `COPY` both `project/engine/` and `project/backend/` — the engine is a relative `require()` dependency of the backend, not an npm package.

## JSON-RPC wire format

Single `POST /api` (or whatever path the Runner is configured to call — the path itself isn't fixed by spec, just convention) endpoint:
```
Request:  { jsonrpc: "2.0", id, method: "play", params: {...} }
Response: { jsonrpc: "2.0", id, result: {...} }
```
Reference plumbing (`./info/sample-game-main/backend/src/index.js`) uses plain Express + CommonJS + a `HANDLERS` object keyed by method name — this is the style to imitate; that sample's actual game logic (a 50/50 coin-flip) is not.

## RTP guidance

- Not required, but BGaming "strongly suggests" two RTP variants: ~96-97.5% and ~94-94.5% (`Questions.txt`). The Python prototype targets 96.00% (`game_config.py: self.rtp = 0.9600`) — treated as the primary/first-pass target; a second lower-RTP variant is explicitly deferred scope (see `docs/architecture.md`).
- Math/RTP must be independently verifiable — our offline simulation CLI (`sim/`) exists specifically to produce this documentation (RTP, hit rate, volatility, feature frequencies) ahead of any real submission.

## Out of scope for this project (Runner/frontend/asset responsibilities, not ours)

`init`/`info`/`replay` RPC methods, balance ledger, session management, `state_lock` issuance, autoplay UI, gamble/risk UI, paytable/rules UI, localization strings (incl. mandatory Social English), all graphics/audio asset deliverables, the clickable prototype / GDD slide deck / marketing materials required for actual submission. These are noted here only so they aren't accidentally assumed to be part of the backend's job.
